# NeuroCasper

Telegram-бот, который следит за стримерами на YouTube/TikTok/Kick и
присылает уведомление «в эфире» или «новое видео» в Telegram-канал или
группу — с кнопкой на каждую платформу, объединяя в одно сообщение, если
стример в эфире сразу на нескольких отслеживаемых платформах. У каждого
стримера также могут быть статичные ссылки (Twitch, Discord, второй канал —
что угодно), которые показываются в каждом уведомлении независимо от того,
какая платформа его вызвала — см. «Дополнительные ссылки» ниже.

Интерфейс бота — только на русском.

## Как это устроено

- **Cloudflare Worker** (`src/`) — сам бот (grammY) и проверка YouTube/TikTok
  по расписанию (`src/scheduled.ts`, Cloudflare Cron Trigger, каждые 5 минут).
  Раньше проверка была отдельным скриптом на GitHub Actions cron — перенесена
  сюда, потому что точность расписания GitHub Actions недостаточна для
  интервала в 5 минут: были задержки до часа, это задокументированное
  ограничение самого GitHub Actions для низкоактивных репозиториев, не баг в
  коде. Cron Triggers выполняются на инфраструктуре Cloudflare — той же, где
  крутится сам воркер — и держат расписание намного точнее. Kick устроен
  иначе — не опрашивается по расписанию, а сам присылает вебхук на
  `/kick/webhook`, как только стример начинает или заканчивает эфир (см.
  раздел «Kick» ниже).
  Аккаунты проверяются параллельно (`src/lib/concurrency.ts`), а не один за
  другим — не более 6 одновременно (ровно столько исходящих соединений
  разрешает Cloudflare на один запуск воркера, см. комментарий в этом
  файле). Если у одного стримера отслеживается сразу несколько платформ
  (например, YouTube и TikTok), их проверки внутри одного запуска
  сериализуются между собой через `src/lib/streamer-serializer.ts` — иначе
  при одновременном старте эфира на обеих платформах гонка могла бы
  привести к двум отдельным постам вместо одного объединённого.
- **Cloudflare D1** (`schema.sql`) — пользователи, каналы, стримеры,
  отслеживаемые аккаунты, дополнительные ссылки, состояние отправленных постов.
- **Деплой воркера** — через встроенную Git-интеграцию Cloudflare (подключить
  репозиторий в дашборде, дальше собирается и деплоится на каждый пуш).
- **GitHub Actions** — используется для разовых/вспомогательных задач:
  создание и миграция базы (`1-bootstrap-db.yml`), синхронизация секретов
  воркера (`0-sync-secrets.yml`, нужен из-за особенности Git-интеграции —
  см. ограничения ниже), установка Telegram-вебхука (`2-set-webhook.yml`),
  разовые миграции уже развёрнутой базы (`3-migrate-kick.yml` добавляет
  Kick, `4-migrate-live-post-uniqueness.yml` и `5-migrate-post-claims.yml`
  вместе закрывают дублирование постов — подробнее в разделе «Известные
  ограничения»). Отдельно — `ci.yml`, который проверяет типы
  (`npm run typecheck`) и прогоняет тесты (`npm test`) на каждый push и
  pull request, но сам ничего не деплоит и не трогает; это не разовая
  задача, а обычная проверка на каждое изменение.

`src/lib/publish.ts` реализует правило «опубликовать или объединить»: если
платформа стримера выходит в эфир (или публикует новое видео), а для этого
же стримера уже есть открытый пост — кнопка новой платформы добавляется в
него вместо отдельного сообщения. Кнопка убирается, когда платформа
заканчивает эфир; пост открепляется и закрывается, когда закончили все
отслеживаемые платформы под ним. Перед тем как создать НОВЫЙ пост (когда
объединять ещё не с чем), функция сначала «застолбляет» это место в базе
(`post_claims`, `src/db.ts`) — так, даже если два «в эфире» для одного и
того же стримера обрабатываются в двух разных запусках воркера одновременно
(например, вебхук Kick прилетел ровно в момент, когда крон проверяет
YouTube/TikTok того же стримера), в Telegram уйдёт ровно одно сообщение, а
не два. Подробности и почему это было не так раньше — см. «Известные
ограничения».

## Дополнительные ссылки (где живёт Twitch)

Twitch изначально был третьей отслеживаемой платформой (вебхук EventSub,
пуш-уведомления в реальном времени), но был убран: регистрация приложения
разработчика в Twitch требует 2FA на аккаунте, а это не всем доступно
(например, из-за недоставки SMS в некоторые регионы). Вместо того чтобы
блокироваться на этом, Twitch (и что угодно ещё — Discord, второй канал,
донат-страница) теперь **дополнительная ссылка**: название кнопки + URL,
привязанные к стримеру через `/add_social`, показываются кнопкой в *каждом*
уведомлении этого стримера, живом или видео, независимо от того, какая
отслеживаемая платформа вызвала пост.

Это осознанный компромисс: нет проверки, что Twitch (или что угодно по
ссылке) реально в эфире в этот момент — только предположение, что стример,
который вещает одновременно в нескольких местах, обычно в эфире везде,
когда в эфире хотя бы одна отслеживаемая платформа. `src/lib/buttons.ts`
узнаёт несколько распространённых названий (twitch/discord/instagram/
telegram/x/vk/boosty, без учёта регистра) и даёт им подходящий эмодзи;
всё остальное получает обычную 🔗.

## Kick

В отличие от YouTube (публичный RSS) и TikTok (публичная страница профиля),
у Kick нет способа анонимно или по опросу узнать, идёт ли эфир — только
`events:subscribe`, который присылает вебхук для канала, но лишь после того,
как **сам стример** (не тот, кто держит бота) один раз пройдёт OAuth Kick и
разрешит доступ. Поэтому у Kick в `/add_social` не «отправьте юзернейм», а
кнопка со ссылкой на авторизацию: стример открывает её в своём браузере,
логинится на Kick, разрешает доступ — после чего Kick перенаправляет на
`/kick/oauth/callback`, бот получает токен, подписывается на
`livestream.status.updated` для этого канала и присылает подтверждение в
личку тому, кто это затевал. Дальше уведомления «в эфире»/«не в эфире»
приходят на `/kick/webhook` пушем, в реальном времени — без 5-минутной
задержки, свойственной опросу YouTube/TikTok. Подпись каждого вебхука
проверяется RSA-ключом Kick (`src/lib/kick.ts`, схема подтверждена по
официальной документации Kick field-for-field, включая их собственный
пример проверки подписи на Go) — см. тесты в `src/lib/kick.test.ts`,
реально подписывающие и проверяющие вебхук локальным ключом, раз проверить
это против настоящей инфраструктуры Kick в песочнице, где собирался бот, было
нельзя (см. «Известные ограничения»).

Из этого вытекают отличия, о которых стоит знать:

- **Отвязка Kick через `/settings` сама отписывает бота от вебхука** — при
  отвязке аккаунта или удалении стримера целиком (`/settings` → «👤
  Управлять стримерами», см. «Использование бота») `src/lib/removal.ts`
  вызывает `unsubscribeFromEvents` из `src/lib/kick.ts`, обновив токен
  через `refreshAccessToken`, если он к этому моменту истёк (проверяется
  по `kick_tokens.expires_at`). Если это не получилось (Kick API
  недоступен, приложение уже отозвано самим стримером в его настройках
  Kick) — сама привязка в боте всё равно удаляется, просто подписка на
  стороне Kick доживёт до автоматической отписки по бездействию (см.
  следующий пункт), а не отменится немедленно.
- **Если `/kick/webhook` не отвечает целые сутки** (авария воркера, D1
  недоступна, неудачный деплой) — Kick сам молча отписывает бота от
  события для всех подписанных стримеров, без отдельного сообщения об этом
  где-либо ещё. Если уведомления «в эфире» для стримера с Kick вдруг
  перестали приходить — первое, что нужно проверить, что воркер вообще
  отвечает; если да, а уведомлений всё равно нет, придётся заново пройти
  `/add_social` → Kick для этого стримера, чтобы переподписаться.
- **Токен доступа не обновляется сам по себе, пока не понадобится.** Получать
  сами уведомления это не мешает — Kick держит подписку активной на своей
  стороне после выдачи. `refreshAccessToken` в `src/lib/kick.ts`
  используется только тогда, когда токен реально нужен для вызова Kick API
  (сейчас — единственный такой случай — отвязка стримера/аккаунта, см. выше),
  и только если `kick_tokens.expires_at` уже прошёл.

## Деплой

### 0. Разовые аккаунты/учётные данные

- Токен Telegram-бота: напишите [@BotFather](https://t.me/BotFather) → `/newbot`
- Аккаунт Cloudflare (Workers + D1 бесплатны) — понадобится **Account ID**
  (правый сайдбар дашборда, или прямо в адресной строке браузера)
- Токен Cloudflare API: дашборд → My Profile → API Tokens → Create Token →
  права **Account → D1 → Edit** И **Account → Workers Scripts → Edit** (оба
  нужны — без второго падает синхронизация секретов воркера)
- (Настоятельно рекомендуется, не только «опционально») Ключ YouTube Data
  API v3: [console.cloud.google.com](https://console.cloud.google.com) →
  включить API (YouTube Data API v3) → Credentials → API key. Без этого
  ключа прямой эфир на YouTube почти никогда не определяется как «эфир» —
  из-за блокировки YouTube запросов с серверных IP (см. «Ограничения»,
  там же — почему это приводило к отдельным постам YouTube вместо кнопки
  в уже опубликованном посте Kick) бот почти всегда падает на менее
  надёжную эвристику. Добавляется как секрет, не как `[vars]`: создайте
  репозиторный секрет с именем `YOUTUBE_API_KEY` (GitHub → Settings →
  Secrets and variables → Actions → New repository secret), затем в
  `.github/workflows/0-sync-secrets.yml` раскомментируйте (уберите `#`)
  две строки, явно для этого оставленные в комментарии в начале файла —
  одну в списке `secrets:`, другую в `env:` — и запустите этот workflow
  вручную один раз (дальше он и так срабатывает на каждый пуш)
- (Опционально, но нужно для Kick) Приложение на
  [kick.com/settings/developer](https://kick.com/settings/developer) →
  **Client ID** и **Client Secret**. При регистрации Redirect URI указать
  `<WORKER_URL>/kick/oauth/callback`, где `<WORKER_URL>` — тот же адрес, что
  в `[vars] WORKER_URL` в `wrangler.toml` (по умолчанию
  `https://neurocasper.webtkachdenis.workers.dev`, поменяйте на свой, если
  деплоите под другим именем/доменом) — без точного совпадения авторизация
  стримера на Kick не сработает. Без этих двух ключей платформа Kick просто
  не будет предлагаться в `/add_social` (см. «Kick» выше).

Ничего из этого не может сделать ассистент за вас — каждый пункт требует
входа именно под вашим аккаунтом на соответствующей площадке.

### 1. Репозиторий

Код должен быть в GitHub-репозитории, который вы контролируете —
Git-интеграция Cloudflare и GitHub Actions читают прямо из него на каждый
пуш в `main`.

### 2. Воркер — через Git-интеграцию Cloudflare

Workers & Pages → воркер → подключён к репозиторию, с настройками:

- Build command: `npm run build`
- Deploy command: `npx wrangler deploy`

Что нужно один раз:

- **База D1**: Storage & databases → D1 → Create database → id вставить в
  `database_id` в `wrangler.toml`, закоммитить, запушить. (Тот же результат
  даёт `1-bootstrap-db.yml` из вкладки Actions — он ещё и сразу применяет
  `schema.sql`.)
- **Секреты**: `BOT_TOKEN`, `WEBHOOK_SECRET`, `KICK_CLIENT_ID`,
  `KICK_CLIENT_SECRET` — через `0-sync-secrets.yml` (Actions → Run workflow,
  нужны те же секреты и в GitHub тоже — Settings → Secrets and variables →
  Actions) или вручную через Settings → Variables and Secrets у воркера (но
  см. ограничение ниже про то, почему это может не пережить следующий
  деплой). Если Kick не используете — заведите оба `KICK_*` секрета в GitHub с
  любым непустым значением-плейсхолдером: `0-sync-secrets.yml` синхронизирует
  их безусловно (в отличие от `YOUTUBE_API_KEY`, см. комментарий в файле
  workflow, почему) и упадёт с ошибкой, если хоть одного из них нет в
  GitHub вообще. `YOUTUBE_API_KEY` в этот список не входит по умолчанию —
  если понадобится, добавляется отдельно, тоже по инструкции в файле
  workflow.

### 3. Направить Telegram на воркер

После деплоя и когда `BOT_TOKEN`/`WEBHOOK_SECRET` установлены — запустите
`2-set-webhook.yml` вручную из вкладки Actions (нужны те же два секрета в
GitHub тоже). Обновлённый `allowed_updates` в этом файле включает
`chat_member` — без повторного запуска после обновления бота Telegram не
пришлёт события вступления участников, и приветствие с проверкой на спам
работать не будут (жалобы через `/report` от этого не зависят — это
отдельный тип обновления, `message`, который уже был включён).

### 4. Миграции для уже работающей базы

Для **нового** деплоя ничего дополнительно делать не нужно — `schema.sql`
уже содержит все таблицы и столбцы, включая систему жалоб, настройки
модерации, уведомление о выходе участника и АнтиСсылку. Для **уже
развёрнутого** бота, где база создавалась раньше, — примените файлы из
`migrations/` по номеру, каждый ровно один раз:

```
npx wrangler d1 execute neurocasper-db --remote --file=./migrations/004_add_user_reports.sql
npx wrangler d1 execute neurocasper-db --remote --file=./migrations/005_add_moderation_settings.sql
npx wrangler d1 execute neurocasper-db --remote --file=./migrations/007_add_welcome_delete_after.sql
npx wrangler d1 execute neurocasper-db --remote --file=./migrations/008_add_leave_message.sql
npx wrangler d1 execute neurocasper-db --remote --file=./migrations/009_add_antilink.sql
```

(сначала без `--remote` — против локальной базы; каждая из них использует
`ALTER TABLE ADD COLUMN`, у SQLite нет `IF NOT EXISTS` для колонок, так что
повторный запуск любой из них упадёт с «duplicate column name» — это
безопасно, значит уже применено). Более ранние `migrations/001`–`003`,
если ещё не применялись, — по тому же принципу и в том же порядке. Номера
файлов в `migrations/` не идут подряд без пропусков (нет `006` — это не
ошибка, просто такой файл никогда не создавался).

Для `005`, `007`, `008` и `009` то же самое можно сделать без терминала,
прямо со страницы Actions в GitHub (вкладка **Actions** → нужный workflow
→ **Run workflow**): `6-migrate-moderation-settings.yml` (несмотря на
номер в своём названии, применяет именно `005_add_moderation_settings.sql`
— номер в имени workflow-файла отражает порядок их создания, а не номер
файла миграции, который он запускает), `9-migrate-welcome-delete-after.yml`,
`7-migrate-leave-message.yml` и `8-migrate-antilink.yml`. Все они сами
проверяют, применена ли уже соответствующая миграция, и ничего не ломают
при повторном запуске.

## Известные ограничения (важно прочитать)

- **У кнопок Telegram нет настройки цвета** — Bot API этого не даёт, поэтому
  «цветные кнопки» в буквальном смысле недостижимы. Реализовано: цветной
  кружок-эмодзи в подписи кнопки (🔴 YouTube / ⚫ TikTok / 🟢 Kick / 🟣 Twitch
  как доп.ссылка). Полный контроль цвета есть только у сгенерированной
  запасной картинки-превью — это уже пиксели, которые рисует сам бот.
- **Kick — см. отдельный раздел «Kick» выше** для того, как он устроен и чем
  отличается от YouTube/TikTok; коротко — свои ограничения есть и у него
  (молчаливая отписка от вебхука через 24 часа простоя, токен не
  обновляется сам по себе вне момента отвязки — см. ниже).
- **Дополнительные ссылки (Twitch и т.п.) никогда не проверяются** — см.
  раздел выше. Кнопка показывается в каждом уведомлении стримера без
  проверки актуальности в конкретный момент.
- **Секреты воркера, добавленные через дашборд Cloudflare, не всегда
  переживают автодеплой** через Git-интеграцию — на практике `BOT_TOKEN`/
  `WEBHOOK_SECRET` пропадали через несколько автодеплоев после ручного
  добавления. Причина до конца не выяснена (похоже на особенность привязки
  переменных к конкретной версии, а не к воркеру целиком в модели Versions).
  Поэтому секреты лучше ставить через `0-sync-secrets.yml` (`wrangler
  secret put`, прикрепляется к воркеру, а не к версии) и перезапускать этот
  workflow после каждого автодеплоя, если бот вдруг перестал отвечать —
  первым делом проверить именно это.
- **Почему кнопка YouTube/TikTok иногда не подтягивалась ко уже
  опубликованному посту Kick (и как это исправлено)** — реальный,
  воспроизведённый баг, а не гипотеза: когда один стример заявлен сразу на
  нескольких платформах, пост объединяется в одно сообщение только если у
  новой платформы при публикации совпадает `kind` ("live" или "video",
  `publishOrMerge` в `src/lib/publish.ts`) с уже открытым постом —
  `findOpenPost` ищет именно по этой паре. До этого исправления YouTube без
  `YOUTUBE_API_KEY` узнавал про прямой эфир ТОЛЬКО эвристикой по разметке
  страницы просмотра (`isLiveNow`/`liveBroadcastContent` в HTML) — а с
  конца 2025 года YouTube массово и задокументированно отдаёт запросам с
  серверных/датацентровых IP (ровно то, откуда приходит `fetch` из
  Cloudflare Workers) страницу-заглушку «Sign in to confirm you're not a
  bot» вместо настоящей, без этих меток вообще. Из-за этого прямой эфир на
  YouTube почти всегда определялся как `kind: "video"`, а не `"live"`, и
  создавал **отдельный** пост вместо того, чтобы подтянуть кнопку к уже
  существующему посту Kick — именно баг, который был описан в задаче на
  доработку. Источники (независимые, несколько): пример на Scrapfly (у них
  же — советы по сервисам обхода на базе residential-прокси для этой самой
  проблемы) и ряд независимых обсуждений той же блокировки для
  Vercel/AWS Lambda/Cloudflare Workers.
  **Исправление**: `checkChannelLiveNow` (`src/lib/youtube.ts`) теперь, при
  заданном `YOUTUBE_API_KEY`, в первую очередь запрашивает официальный
  Data API v3 (`search.list` c `eventType=live`) — это не скрейпинг
  страницы, а штатный, документированный способ, под блокировку
  датацентровых IP не подпадающий (она действует именно на обычные
  веб-страницы YouTube, а не на `googleapis.com`), и в одном ответе даёт и
  `videoId`, и `title`, и настоящее превью. Если ключ не задан, или
  официальный вызов сам не удался (сеть, исчерпанная квота, сбой на
  стороне YouTube) — используется прежняя эвристика по разметке страницы,
  честно и с полным пониманием её ненадёжности, но не как единственный
  путь. Важная оговорка по квоте: `search.list` стоит 100 единиц за вызов
  (большинство других вызовов Data API, включая уже использовавшийся здесь
  `videos.list`, стоят 1) из бесплатного дневного лимита в 10 000 единиц на
  ключ — вызывается не на каждом тике крона, а только пока для аккаунта
  ещё нет открытого live-поста (ровно так же, как раньше был устроен
  старый эвристический путь), так что при разумном числе отслеживаемых
  YouTube-каналов это укладывается в лимит, но ключ, разделяемый с другими
  потребителями квоты, или очень большое число каналов на коротком
  интервале крона всё же могут его исчерпать — тогда до сброса квоты (раз
  в сутки) используется запасной путь.
- **Лишний пустой ряд в конце клавиатуры у каждого поста о стриме** —
  безвредно для отображения (Telegram просто не рисует пустой ряд), но
  реальный, подтверждённый прогоном настоящего кода дефект, который
  `buildKeyboard` (`src/lib/buttons.ts`) выдавал на **каждом** вызове:
  `InlineKeyboard.row()` в grammY всегда начинает новый пустой ряд, не
  проверяя, добавили ли в текущий хоть одну кнопку, так что вызов его
  после последней кнопки в цикле (а не между кнопками) неизбежно оставляет
  один пустой ряд в хвосте. Тот же паттерн нашёлся ещё в пяти местах
  (`promptChannelChoice`, `promptStreamerChoice`, `promptPlatformChoice`,
  экран авторизации Kick, и дважды внутри `handleSettingsCallback`) —
  исправлено везде одинаково: `.row()` вызывается только **между**
  кнопками, никогда после последней. Отдельно стоит того, что до этого
  сам баг был не исправлен, а замаскирован: `buttons.test.ts` уже
  содержал собственный комментарий, прямо признающий дефект, и
  вспомогательную функцию `flatten()`, которая через `.flat()` незаметно
  «съедала» пустые ряды при сравнении — тесты проходили что с багом, что
  без него, не видя разницы. Теперь там же есть отдельный, не маскируемый
  тест именно на отсутствие пустых рядов.
- **Приветствие, проверка на спам и `/report` требуют, чтобы бот был
  администратором** именно той группы. Это ограничение самого Telegram Bot
  API, не этого кода: событие о вступлении участника (`chat_member`)
  Telegram присылает только для чатов, где бот — админ; `/report` находит
  нарушителя и записывает жалобу в любом случае, но заблокировать
  участника (`banChatMember`) без прав администратора физически не может.
  В каналах (в отличие от групп) у `chat_member` нет смысла — там нет
  привычного «участник вступил», поэтому приветствие и спам-фильтр там не
  применяются вовсе.
- **У TikTok вообще нет публичного API** для статуса эфира или списка видео.
  `src/lib/tiktok.ts` парсит публичную страницу профиля в поисках метки
  `roomId` и ссылки на последнее видео. При изменении разметки TikTok может
  тихо перестать что-либо находить — это самое ненадёжное звено из двух
  отслеживаемых платформ. У постов TikTok также не будет заголовка (нет
  надёжного способа его получить без API) — только шапка с именем стримера.
  Та же страница теперь дополнительно парсится и на превью live-комнаты
  (`"cover":{"url_list":[...]}`, тот же JSON-блок рядом с `roomId`, в
  формате, которым TikTok представляет практически любую картинку в своём
  продукте, — подтверждено только по независимым сторонним SDK/библиотекам,
  официальной документации нет в принципе, т.к. нет самого API) — но это
  именно попытка, не гарантия: воспроизвести это против настоящей,
  реально идущей трансляции не было возможности (а против кода, который
  это даже не пытался искать, тоже негде было сверить), так что в
  реальности это может оказаться совпадением чаще, чем нет, и TikTok
  по-прежнему нередко останется на сгенерированной запасной картинке. Если
  после обновления у вас в логах видно, что для TikTok регулярно не
  находится превью, — это ожидаемо, а не повод считать код сломанным.
- **Превью для Kick** — вебхук `livestream.status.updated` (тот, что бот
  уже получает) не содержит превью вообще; `src/lib/kick.ts` теперь

  переавторизация уже подключённых Kick-аккаунтов не нужна) сразу после
  вебхука. Точная структура JSON-ответа V2 подтверждена **не** прямой
  выдержкой из `docs.kick.com` (страницу с этим конкретным эндпоинтом не
  удалось открыть напрямую при разработке), а по сходству с уже
  работающим в этом же файле `fetchOwnChannel` (тот же `{data: [...]}`,
  уже подтверждённый против `/public/v1/channels`) и перекрёстно — по
  нескольким независимым сторонним Kick API-клиентам, согласным друг с
  другом в деталях. Если Kick когда-нибудь действительно изменит форму
  ответа, `fetchLivestreamThumbnail` просто вернёт `null` (она на это
  явно рассчитана — падает закрыто, не бросает исключение), и Kick
  вернётся к сгенерированной запасной картинке — не к ошибке. Заодно
  реализовано и обновление токена перед этим вызовом (`expires_at` +
  `refreshAccessToken`) — раньше в коде было открыто написано, что
  `refreshAccessToken` существует, но никем не вызывается, так как до
  этого ни одна операция не обращалась к Kick API достаточно регулярно,
  чтобы это стало важным; этот вызов — первая такая операция.
- **Почему нажатие кнопки настройки иногда выглядело так, будто вообще
  ничего не произошло (например, тумблер «Включить АнтиСсылку») — и как
  это исправлено, причём не только для этого одного тумблера** — реальный,
  воспроизведённый баг с конкретной прослеженной причиной: если
  обработка нажатой кнопки падает с любой ошибкой (например, миграция
  под новую колонку `channels` ещё не применена к боевой базе, а код,
  который её уже ждёт, уже задеплоен), эта ошибка раньше долетала только
  до `console.error` внутри `bot.catch` (`src/bot.ts`) — ни самому
  человеку, ни кому-либо ещё без доступа к логам воркера её увидеть было
  негде. Хуже того: `bot.on("callback_query:data", ...)`
  (`src/handlers/telegram.ts`) отвечал на нажатие (`answerCallbackQuery`)
  безусловно, в `finally`-блоке — то есть даже при падении обработчика. А
  Telegram учитывает только **первый** такой ответ на одно нажатие — все
  последующие попытки ответить на то же нажатие ни к чему не приводят, в
  том числе молча для любого кода уровня Bot API (подтверждено несколькими
  независимыми сторонними отчётами о том же самом). Из-за этого пустой
  ответ из `finally` «съедал» единственную возможность показать
  по-настоящему что-то полезное ещё до того, как ошибка вообще доходила
  до `bot.catch`. **Исправлено**: `finally`-блок убран — если обработка
  упала, строка с `answerCallbackQuery` просто не выполняется, оставляя
  единственную попытку свободной; `bot.catch` теперь сам пытается
  реально сообщить человеку (через `answerCallbackQuery` с
  `show_alert: true` для нажатой кнопки, через обычный `ctx.reply` для
  остальных сообщений), текстом без технических подробностей самой
  ошибки (её детали остаются только в логе воркера) — через новую функцию
  `notifyUserOfError` (`src/bot.ts`, покрыта юнит-тестами). Это
  исправление касается **не только** конкретного тумблера АнтиСсылки, с
  которого расследование началось, а вообще любой будущей ошибки в
  обработке любой кнопки бота — раньше любая такая ошибка выглядела бы
  одинаково: нажатие «проглочено», ничего не произошло, без единой
  подсказки, в чём дело. Практический совет конкретно для кнопки
  АнтиСсылки: если после этого обновления при нажатии всё ещё ничего не
  видно (без алерта об ошибке) — скорее всего, правки кода ещё не
  задеплоены вообще. Если теперь виден алерт с ошибкой — почти наверняка
  дело в непримененной миграции `009`: на вкладке Actions в GitHub
  запустите `8-migrate-antilink.yml` (он сам проверяет, нужно ли это, и
  ничего не испортит, если уже применено).

  бронь, независимость разных `streamer_id`/`kind` друг от друга, а
  «протухшая» бронь остаётся некрадомой, пока не устареет по-настоящему —

  адрес получения публичного ключа
  (`api.kick.com/public/v1/public-key`) сверен только по документации Kick

  клавиатурами, `/report`, приветствие и уведомление о выходе участника,
  блокировка участника, удаление сообщения по АнтиСсылке) тестами не
  покрыты вообще — первое реальное использование после деплоя остаётся
  первой настоящей проверкой для них. YouTube/TikTok/Kick
  (`src/lib/youtube.ts`, `src/lib/tiktok.ts`, `src/lib/kick.ts`) — иначе:
  логика парсинга, выбора между официальным API и эвристикой, и
  обработки ошибок (сеть упала, ответ не 200, поле отсутствует) проверена
  юнит-тестами с замоканным `fetch` (`npm test`), но ни разу не вызывалась
  против настоящего `googleapis.com`, `tiktok.com` или `api.kick.com` —
  только воспроизводящих реальную документированную форму ответа заглушек.
  Против реальной локальной D1 (через
  `node:sqlite` и актуальный `schema.sql`, не переписанная вручную копия
  таблицы) проверена логика хранения для системы жалоб — что одна и та же
  группа не может дважды засчитаться в счётчик на одного человека
  (`UNIQUE` в `user_reports`, см. `migrations/004`), а жалобы из разных
  групп считаются верно — и для настроек модерации на чат — переключатели,
  свой текст приветствия и свой список спам-фраз действительно сохраняются

  стандартным значениям при сбросе; так же точно проверены (реальная

  сброс и значения по умолчанию для свежесозданного чата. Оценка даты
  регистрации по ID аккаунта
  (Bot API не отдаёт её никак) сверена с независимым пересчётом по тому же
  открытому набору калибровочных точек и тому же алгоритму, на которых она
  основана (`src/lib/registration-date-estimate.ts`), но остаётся именно

  очень новых аккаунтов (новее последней калиброванной точки набора) —
  грубее; в тексте приветствия это помечено явно.
- **Дубль поста при почти одновременном «в эфире» на двух платформах** —
  раньше была теоретическая гонка: если для одного стримера два события «в
  эфире» (например, вебхук Kick и проверка YouTube/TikTok по расписанию)
  обрабатывались достаточно близко по времени, оба могли не увидеть
  открытый пост друг друга и создать два отдельных сообщения в Telegram
  вместо одного объединённого. С миграцией
  `002_add_live_post_unique_constraint.sql` это перестало проходить
  незаметно (вторая попытка записи в базу падала с ошибкой, уже
  отлавливаемой и логируемой), но не убирало сам дубль сообщения — оно к
  этому моменту обычно уже было отправлено. С миграцией
  `003_add_post_claims.sql` (`5-migrate-post-claims.yml`) и переписанным
  `publishOrMerge` в `src/lib/publish.ts` гонка закрыта по-другому: перед
  тем как отправить сообщение в Telegram, функция сначала пытается
  «застолбить» это место в базе (`post_claims`); если кто-то параллельный
  уже застолбил его первым, функция ждёт и перепроверяет — и в норме
  находит уже созданный тем, первым, пост и просто добавляет в него свою
  кнопку, вместо того чтобы отправлять своё сообщение вообще. Проверено
  против реальной локальной D1 (см. выше), но не против одновременных
  настоящих вебхука Kick и запуска крона — стоит последить за логами
  воркера первое время после обновления на всякий случай.
- **Отвязка стримера/аккаунта не тестировалась на живом Telegram-боте** —

- **Уведомление о выходе участника, спам-фразы без ограничения по
  количеству и АнтиСсылка** — три функции, добавленные позже остального
  (`migrations/008` и `migrations/009`), той же рабочей средой без
  доступа к `api.telegram.org` (см. пункт выше), поэтому тот же вопрос
  «первое реальное использование после деплоя — первая настоящая
  проверка» относится и к ним:
  - **Уведомление о выходе** — та же точка Bot API (`chat_member`), что
    уже используется для приветствия, просто для противоположного
    перехода статуса (`isMemberStatus` переходит из «был участником» в
    «не стал»); сам переход и текст с подстановками проверены юнит- и
    интеграционными тестами, отправка реального сообщения в реальную
    группу — нет.
  - **Список спам-фраз без лимита** — экран теперь листается страницами

    сообщение, который без пагинации был бы легко превышен при большом
    списке). Пагинация и сами фразы по умолчанию (теперь их 77 —
    добавлены все переданные при доработке, поверх уже бывших в боте)
    проверены юнит-тестами; как именно выглядит и листается сам экран в
    настоящем Telegram — нет.
  - **АнтиСсылка** — удаляет сообщение в группе, если найденная в нём
    ссылка (включая скрытую за другим текстом — `text_link` в терминах
    Bot API) не совпадает ни с одним доменом из белого списка этого чата;
    администраторов группы (включая её создателя) не проверяет. Вся
    логика поиска ссылок и сравнения с белым списком (`src/lib/
    antilink.ts`) — чистые функции, без обращения к сети — покрыта
    юнит-тестами отдельно от Telegram. Не проверено на живых данных: как
    Telegram на самом деле размечает `entities`/`caption_entities` для
    разных реальных способов вставить ссылку (обычный текст, ссылка под
    другим текстом, пересланное сообщение, сообщение с фото и подписью) —
    тесты используют вручную собранные объекты той же формы, что
    документирует Bot API, а не настоящие апдейты от Telegram; удаление
    чужого сообщения (`deleteMessage`) и проверка прав отправителя
    (`getChatMember`) самой сетью тоже не вызывались ни разу. При первом
    включении в настоящей группе стоит сначала добавить в белый список
    всё нужное и последить за логами воркера, прежде чем полагаться на
    автоматическое удаление без присмотра.

## Использование бота

- `/start` — обзор
- В **группе**: `/add_channel` (бот уже должен быть там админом)
- Для **канала**: перешлите любой пост из него боту в личку (бот уже должен
  быть там админом)
- В личке: `/add_social` — выбрать канал, затем существующего или нового
  стримера, затем YouTube/TikTok (отправить юзернейм), Kick (кнопка
  авторизации — открыть её должен сам стример, см. раздел «Kick» выше) или
  «Добавить ссылку» (название кнопки, потом URL — сюда идёт Twitch)
- В личке: `/settings` — переключить автозакрепление/автооткрепление,
  изменить текст уведомления (`{title}` `{game}`), увидеть всё привязанное
  к каждому стримеру, а через «👤 Управлять стримерами» — отвязать один
  аккаунт или дополнительную ссылку у стримера, либо удалить стримера
  целиком (с подтверждением на каждое действие; для Kick отвязка сама
  отписывает бота от вебхука на стороне Kick, см. «Известные ограничения»),
  а через «👥 Модерация группы» — настройки приветствия и спам-фильтра
  этого чата (см. ниже)
- В **группе** (бот там должен быть админом — иначе `/report` найдёт
  участника, но заблокировать его не сможет): ответьте `/report` на
  сообщение нарушителя. Жалобы от одной и той же группы на одного человека
  считаются как одна (защита от сговора нескольких участников одной
  группы); когда жалобы приходят минимум из **двух разных** групп — бот
  блокирует участника на 30 дней всюду, где сам является админом (сразу
  в группе, где счёт набрался, и при каждой попытке вступить в любую
  другую такую группу впоследствии)
- Приветствие новых участников (кто вступил, фото профиля, ник,
  приблизительная дата регистрации — Bot API не отдаёт её напрямую, это
  оценка по ID аккаунта) и проверка описания профиля на спам-фразы при
  вступлении включены по умолчанию для каждой группы, где бот админ;
  текст приветствия, список фраз и оба переключателя — через
  «👥 Модерация группы» в `/settings`, заданные изначально значения
  меняются и дополняются прямо там

## Локальная разработка (опционально — для деплоя не обязательно)

```bash
npm install
cp .dev.vars.example .dev.vars   # заполнить реальными или тестовыми значениями
npm run db:migrate:local
npm run dev            # wrangler dev --test-scheduled
npm run typecheck
npm test                # src/**/*.test.ts, через tsx --test — офлайн, сеть не нужна
```

`ci.yml` (см. «Как это устроено») прогоняет `typecheck` и `test` на каждый
push и pull request — если оба шага прошли локально, CI тоже должен пройти.

Проверить обработчик расписания локально, не дожидаясь реального cron:

```bash
curl "http://localhost:8787/__scheduled?cron=*/5+*+*+*+*"
```
